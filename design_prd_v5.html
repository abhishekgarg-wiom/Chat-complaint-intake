1. Problem Statement

Today, when an ACTIVE or INACTIVE user says "mera net nahi chal raha" (or any seekHelp variant), the chat system routes to a static "Call us" response. No diagnostics, no ticket creation, no self-service. ~1,076 such messages per day in ACTIVE, ~28% frustrated, ~143/day get stuck in repetition loops.

What we're solving: replace the dead-end with a multi-step chat that diagnoses, de-duplicates against existing tickets, guides a restart, and creates the right ticket in Kapture.

2. Jobs To Be Done

User: वर्मा परिवार
🎯 Functional

जब मैं चैट पर अपनी दिक्कत बताऊँ, तो मेरी दिक्कत तुरंत रजिस्टर हो जाए और उस पर काम शुरू हो जाए, ताकि मुझे कॉल करके दोबारा वही बात न बतानी पड़े।

💛 Emotional

जब मेरे इंटरनेट में कोई दिक्कत होती है, तब मैं चाहता हूँ कि मुझे लगे कि मेरी समस्या पर तुरंत ध्यान दिया जा रहा है, ताकि मैं frustration, ignored या helpless महसूस न करूँ।

👥 Social

जब मेरे इंटरनेट में कोई दिक्कत आए, तो मैं चाहता हूँ कि वह जल्दी और आसानी से सुलझ जाए, ताकि मेरे परिवार के लोगों का काम न रुके और मुझे बार‑बार समझाना न पड़े।

🏢 Wiom System Objective

जब वर्मा परिवार chat पर अपनी समस्या बताता है, तब व्योम को उस समस्या को तुरंत system में दर्ज कर उसे सही टीम तक पहुँचाना चाहिए, ताकि complaint का clear ownership बने, repeat effort की जरूरत न पड़े, और silent churn कम हो।

⚙️ CSP Execution Requirement

जब chat के माध्यम से complaint आए, तब CSP को एक साफ, structured और actionable जानकारी मिलनी चाहिए, ताकि वे बिना दोबारा पूछे सीधे समाधान पर काम शुरू कर सकें।

🧠 Clean Framing

जब customer chat पर internet issue बताता है लेकिन उसकी complaint system में दर्ज नहीं होती, तब वह या तो बार‑बार कोशिश करता है या बिना समाधान के छोड़ देता है। व्योम का काम इस dead-end को clear ownership और actionable resolution में बदलना है।

3. Objective

  • Deduplicate — check for open / 48hr-resolved tickets before creating a new one.
  • Diagnose — ping the netbox to know if it's a device or supply-side issue.
  • Self-serve — guide a restart / Wi-Fi correction before escalating.
  • Auto-ticket — create the ticket with full context.
  • Confirm — show the ticket and route the call CTA to the assigned engineer / partner.

6. Design Principles

  • Reduce uncertainty — every diagnostic step is shown to the user (status check rows with ✅ / ❌).
  • Clarify system state — sticky top-of-chat status bar always reflects current net status + active ticket.
  • Coordinate the next action — every bot turn ends with either a clear CTA, a side-by-side choice, or a closing message + restart card.
  • Maintain continuity — ticket info (engineer name, ETA) carries forward across the conversation once created.
  • Empathetic Hindi tone — never ordering, never dismissive; acknowledge before instructing.

8. User Journeys

Gate A pass · Gate B pass · Gate C pass · Gate D pass · Wi-Fi pass

7.1 Happy flow default

Trigger: Active user, no open ticket, no recent resolved ticket, ping OK, on correct Wi-Fi.

  1. User types intent → bot acknowledges plan is active.
  2. Bot runs a visible status check (✅ recharge, ✅ Wi-Fi).
  3. Bot asks "दिक्कत क्या है?" with 2 issue options.
  4. Bot shows guided steps (restart netbox, reconnect Wi-Fi) with a single "हो गया, चेक करते हैं" CTA.
  5. Bot asks "अब सही चल रहा है?" → हाँ: close with success message · नहीं: create ticket, show ticket card + Call CTA.
Gate A fail

7.2 Recharge flow

Trigger: Plan inactive (post-expiry).

  1. User types intent → bot shows recharge-due status.
  2. Bot explains why net isn't working + offers recharge CTA.
  3. No ticket created. Flow ends with restart card.
Gate B fail

7.3 Open ticket already exists

Trigger: An open Type 3 / 4 ticket is already in the system.

  1. User types intent → bot acknowledges and shows the existing ticket details (ID, engineer name, TAT).
  2. Bot tells user no new ticket is needed.
  3. Call CTA → routes to the assigned engineer (existing logic).
  4. Flow ends with restart card.
Gate C fail

7.4 Resolved ticket in last 48 hr

Trigger: A Type 3 / 4 ticket was resolved within the last 48 hours.

  1. Bot recalls the recently resolved ticket and asks "क्या वही दिक्कत वापस आई है?" (side-by-side: हाँ / नहीं).
  2. हाँ, वही दिक्कत → reopen the previous ticket, show updated ticket card + Call CTA, end.
  3. नहीं, अलग है → system runs a fresh ping check and surfaces the result to the user:
    • Ping आ रहा है → system runs a Wi-Fi connection check and surfaces the result:
      • Wi-Fi से जुड़े हैं (✅) — status check shows ✅ recharge active + ✅ correct Wi-Fi. Bot acknowledges "हमारी तरफ़ से सब ठीक दिख रहा है" and asks "दिक्कत क्या है?" with 2 issue options → guided steps (restart netbox + reconnect) → recheck "अब सही चल रहा है?" → हाँ: close · नहीं: create ticket, show ticket card + Call CTA.
      • Wi-Fi से नहीं जुड़े हैं (❌) — status check shows ✅ recharge active + ❌ wrong / no Wi-Fi. Bot skips the "सब ठीक" line and goes straight to "दिक्कत क्या है?" → guided steps (connect to the correct Wi-Fi first, then restart netbox) → recheck → close on success, ticket on failure.
    • Ping नहीं आ रहा → enters the No-ping journey (7.5).
Note: Ping result and Wi-Fi result are diagnostic moments shown to the user as system status checks — not background-only.
Gate D fail

7.5 No ping (netbox unreachable)

Trigger: System cannot reach the customer's netbox.

  1. Bot tells user it can't connect to the netbox and asks "क्या आपका नेट बॉक्स ON है?" (हाँ / नहीं).
  2. हाँ, ON है → fast-path SERVICE ticket auto-created ("इलाके में नेट बंद है"), ticket card + Call CTA shown, end.
  3. नहीं, OFF है → bot guides user through turn-on + Wi-Fi reconnect with a single "अब चेक करें" CTA.
  4. Bot asks "अब सही चल रहा है?" → हाँ: close · नहीं: fast-path SERVICE ticket created, end.
Wi-Fi fail

7.6 Wrong / no Wi-Fi connection

Trigger: Plan active, ping OK, but user is connected to the wrong Wi-Fi (or none).

  1. Bot runs status check (✅ recharge, ❌ Wi-Fi) — user sees the mismatch.
  2. Bot asks issue → guides to connect to the correct Wi-Fi → recheck.
  3. Resolved → close. Unresolved → ticket created.
Gate C variant

7.7 Resolved & closed by user (with rating)

Trigger: Previous ticket was already closed by the user with a rating — no reopen prompt.

  1. Bot acknowledges the closed ticket with a thank-you.
  2. Flow continues fresh — same as Happy flow from the intent step.

9. Common UI Patterns

PatternUsed when
Sticky status bar (top of chat)Always — shows current net status + active ticket line (engineer, ETA) once a ticket exists.
Status check rows (✅ / ❌ stacked)Whenever the system reports a diagnostic — recharge, Wi-Fi, ping. Each check is its own row.
Side-by-side CTA (2 buttons)Binary choices — हाँ / नहीं, ON / OFF, same / different.
In-bubble link CTAsContinuation actions inside the same bot turn — "हो गया, चेक करते हैं", "अब चेक करें".
Issue picker (2 options)"नेट नहीं चल रहा" / "नेट रुक रुक कर चल रहा है" — anchors the troubleshoot copy.
Ticket cardWhenever a ticket is created / reopened — shows ticket ID, problem, TAT line, and Call CTA. No "Track complaint" link (handled by default post-ticket flow).
Call CTAOn ticket cards — routes to the engineer / partner / Wiom owner of that ticket (existing routing).
Restart cardLast bubble of every closed journey — lets the user restart the chat from scratch.

10. Out of Scope

  • Pre-booking / pre-install states (different seekHelp meaning).
  • Callback scheduling, IVR integration, technician dispatch from chat.
  • Post-ticket tracking inside this flow — default post-ticket experience continues to handle it.
  • SLA / TAT enforcement — existing TAT-breach notification system handles it.
  • 4-category × subtype picker, multi-step troubleshoot nudge cadence, mid-flow interrupt & resume, sentiment-based fast-track — deferred.
  • INACTIVE-state bypass to file service complaints — deferred (v2).
